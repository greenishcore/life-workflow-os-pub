## 一、推荐架构：iCloud Drive 为事实源 + CloudKit 做手表投影

调研暴露的核心矛盾是：
**「本地 Markdown 是唯一事实源」与「watchOS 没有文件系统」直接冲突。**

三个选项，我的建议是 C：

| | A. 纯 iCloud Drive | B. 纯 CloudKit | **C. 混合（推荐）** |
|---|---|---|---|
| Mac / iPhone | ✅ 真 Markdown 文件 | ❌ 变成数据库记录 | ✅ 真 Markdown 文件 |
| Obsidian 兼容 | ✅ | ❌ **破坏** | ✅ |
| Apple Watch | ❌ 完全无法接入 | ✅ | ✅ 通过投影 |
| 本地优先原则 | ✅ | ❌ | ✅ |
| 复杂度 | 低 | 中 | 中高 |
| 付费账号 | 不需要 | 需要 | 手表部分需要 |

**C 的具体形态：**

```
        ┌──────────────────────────────────────────┐
        │  iCloud Drive（唯一事实源，真 .md 文件）    │
        │  ~/Library/Mobile Documents/…/LifeOS/    │
        │  ← Obsidian（Mac & iOS）可直接打开同一份     │
        └───────┬──────────────────────┬───────────┘
                │                      │
          ┌─────▼─────┐          ┌─────▼─────┐
          │  macOS    │          │   iOS     │
          │  完整功能  │          │ 捕捉+看板  │
          └─────┬─────┘          └─────┬─────┘
                │   投影 / 回流（双向）    │
        ┌───────▼──────────────────────▼───────────┐
        │  CloudKit 私有库（轻量投影，非事实源）        │
        │  · TodayProjection  今日待推进的想法（只读）  │
        │  · CaptureOutbox    手表写入的捕捉队列        │
        │  · TaskQueue        待 Mac 执行的转换/归档任务 │
        └───────────────────┬──────────────────────┘
                            │
                      ┌─────▼─────┐
                      │  watchOS  │
                      │ 捕捉+一瞥  │
                      └───────────┘
```

**关键规则**（避免混合模式变成一团乱麻）：
1. CloudKit 里的东西**永远不是事实源**，随时可以从 Markdown 重建；
2. 手表只能**写入 Outbox**，永远不直接改想法；
3. iPhone / Mac 谁先上线谁负责**排空 Outbox**，写入 Markdown 后删除队列记录；
4. 冲突解决：以 Markdown 文件的 `updated` 为准，Outbox 只做追加，不做修改。

## 六、明确不承诺的事（避免后期落空）

1. **iOS 端读写 Apple 便签** —— Apple 无公开 API，做不到，任何声称能做的方案都是 Mac 上的 AppleScript。
2. **Apple Watch 上直接建提醒事项** —— EventKit 在 watchOS 禁写，只能回传 iPhone 代办。
3. **iOS 端把 Markdown 转 Word** —— 无可靠纯 Swift 方案。
4. **iOS 端出与 xelatex 同等质量的中文 PDF** —— 自渲染排版能力有差距。
5. **Apple Watch 离线可用完整数据** —— 手表没有 vault，断网时只有缓存的投影。

### 7.1 复合 vault：只同步子集的实现方式

需求是「想法/日记上 iCloud，隐私与大体积内容留本地」。iCloud Drive **没有**官方的
按目录排除机制，所以不能靠标记，只能靠**分根**：

```
逻辑 vault（应用看到的是合并后的单一视图）
├── 【iCloud 根】~/Library/Mobile Documents/iCloud~com~lifeos~workflow/Documents/
│     ├── Inbox/        随手记      ← iPhone 需要
│     ├── Daily/        每日笔记     ← iPhone 需要
│     └── Projects/     想法/项目    ← iPhone 需要
└── 【本地根】~/LifeWorkflowOS/vault/
      ├── Resources/    资料、论文对照（体积大）
      ├── Archive/      归档
      └── Attachments/  转换产物（可重建，不该占 iCloud）
```

**规则**（写进 M1 的实现约束）：
1. `VaultStore` 扫描**多个根**，合并成单一视图；每条记录记住自己属于哪个根；
2. 新建记录按**目录归属**决定落到哪个根（`Inbox/Daily/Projects` → iCloud，其余 → 本地）；
3. 归属可在设置里改；改动只搬文件，不改内容；
4. 两个根**不允许出现同名同路径**的文件，扫描时若发现冲突，以 iCloud 根优先并**告警**，不静默；
5. 本地根不做文件协调，iCloud 根必须走 `NSFileCoordinator`。

> 好处：Obsidian 可以直接把 iCloud 根当一个库打开（手机上也能开），
> 隐私内容完全不出本机，且 `Attachments/` 这种可重建产物不浪费 iCloud 空间。
