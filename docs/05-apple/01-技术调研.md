# Apple 生态原生化 · 技术调研报告

日期：2026-08-19 · 阶段：① 技术调研（三步法第一步）
目标：把 Life Workflow OS 做成 macOS + iOS + watchOS 原生应用（同一代码生态）

> 本文所有结论分两类：**【本机实测】**＝在你这台机器上跑出来的；**【外部调研】**＝检索所得并注明来源。
> 涉及可行性判断的关键结论，一律以本机实测或 SDK 头文件为准。

## 〇、结论先行

| 判断 | 结论 |
|------|------|
| macOS + iOS 双端原生 | ✅ **完全可行**，工具链已实测通过 |
| watchOS 端 | ⚠️ **可行但需先装 SDK**，且能力边界远比预想小（见 §3） |
| 「同一代码生态」 | ✅ 可行，但正确形态是**共享核心 Swift Package + 各端独立 UI**，不是一套 UI 三端复用 |
| Apple 便签（Notes）打通 | ❌ **iOS/watchOS 永久不可行**（无公开 API），仅 macOS 可用 AppleScript |

| 格式互转（PDF/Word） | ✅ macOS 可沿用 pandoc；⚠️ iOS 需换纯 Swift 方案，能力有降级 |
| Git 归档 | ✅ macOS 原生；⚠️ iOS 走 GitHub API 或让 macOS 当网关 |
| 真机部署 | ⚠️ **当前 0 个签名身份**，需先配 Apple ID（见 §7） |

## 二、Apple 数据链路：逐个平台的真实能力

### 2.1 提醒事项 / 日历（EventKit）【SDK 头文件实测】

从 `iPhoneOS26.5.sdk/.../EventKit.framework/Headers` 直接读出：

```objc
requestFullAccessToEventsWithCompletion:     API_AVAILABLE(ios(17.0), macos(14.0), watchos(10.0))
requestFullAccessToRemindersWithCompletion:  API_AVAILABLE(ios(17.0), macos(14.0), watchos(10.0))
```

→ **读取**：三端都支持（watchOS 10+）。

但同一份头文件里有 **10 个 API 被标记 `__WATCHOS_PROHIBITED`**：

```objc
saveReminder:commit:error:        __WATCHOS_PROHIBITED
removeReminder:commit:error:      __WATCHOS_PROHIBITED
saveEvent:span:commit:error:      __WATCHOS_PROHIBITED
removeEvent:span:commit:error:    __WATCHOS_PROHIBITED
saveCalendar:commit:error:        __WATCHOS_PROHIBITED
removeCalendar:commit:error:      __WATCHOS_PROHIBITED
commit:error:                     __WATCHOS_PROHIBITED
refreshSourcesIfNecessary         __WATCHOS_PROHIBITED
```

> **这是硬约束，不是权限问题**：watchOS 上 EventKit **只读**。
> 手表要「新建一条提醒」，只能把意图发回 iPhone 执行（WatchConnectivity / CloudKit 队列）。

### 2.2 Apple 便签（Notes）【外部调研】

**Apple 至今没有任何公开的 Notes API / SDK**，也没有 iCloud Notes 云端接口。
可用的自动化途径只有两条，且都是设备本地的：

| 途径 | 平台 | 说明 |
|------|------|------|
| AppleScript / JXA | **仅 macOS** | Notes.app 有脚本字典，可查询与写入；需「自动化」权限 |
| 快捷指令 Shortcuts | iOS / macOS | **用户主动触发**，App 无法后台读写 |

> **规划影响**：便签打通**只能是 macOS 侧的能力**，且当前项目已用
> `notes-exporter`（AppleScript）实现。iOS 端不要承诺便签同步——做不到。
> iOS 上的等价体验应改为：**分享扩展（Share Extension）+ 快捷指令**，
> 让用户把便签内容「分享到」本应用，而不是应用去读便签。

### 2.3 watchOS 的文件系统与 iCloud【外部调研 + 交叉验证】

- **watchOS 不支持 iCloud Drive**：`ubiquityIdentityToken` 在 watchOS 上恒为 `nil`。
- **App Groups 不能用于 iPhone ↔ Watch 同步**。
- 可用的跨设备通道只有：**CloudKit**（watchOS 3.0+，头文件已确认）与 **WatchConnectivity**。

> **这条决定了整个架构**：「本地 Markdown 文件是唯一事实源」这条原则
> 在 watchOS 上**物理上无法成立**。手表不可能持有 vault。

## 三、watchOS 能力边界总结

| 能力 | 可行性 | 说明 |
|------|--------|------|
| 读日历/提醒 | ✅ | EventKit watchOS 10+ |
| 写日历/提醒 | ❌ | `__WATCHOS_PROHIBITED`，须回传 iPhone 执行 |
| 访问 Markdown vault | ❌ | 无 iCloud Drive，无文件系统共享 |
| CloudKit 读写 | ✅ | watchOS 3.0+ |
| WatchConnectivity | ✅ | 但社区普遍反馈**不稳定**（消息不达、delegate 不触发） |
| 语音输入捕获 | ✅ | Dictation / `TextFieldStyle`，是手表最自然的输入方式 |
| 复杂功能（Complication）/ Smart Stack | ✅ | 适合展示「今日待推进的想法」 |
| 跑格式转换 / git | ❌ | 算力与 API 都不允许 |

> **手表的正确定位：捕捉端 + 一瞥端。**
> 不是「第三个完整客户端」，而是「说一句话就记下来」+「抬腕看今天该推进什么」。
> 强行做完整功能会同时踩上 EventKit 只读、无文件系统、WatchConnectivity 不稳三个坑。

## 四、格式互转（第 3 条主线）在各端的落地

| 环节 | macOS | iOS | watchOS |
|------|-------|-----|---------|
| Markdown 解析 | `apple/swift-markdown`（CommonMark 合规） | 同左 | 不做 |
| Markdown 渲染 | SwiftUI `AttributedString(markdown:)` / MarkdownView | 同左 | 不做 |
| → PDF | 可 shell 调 **pandoc + xelatex**（已有，质量最好） | **不能调 pandoc**，改用 `UIGraphicsPDFRenderer` / `ImageRenderer` 渲染 SwiftUI 视图 | 不做 |
| PDF → Markdown | pandoc / markitdown（现成） | PDFKit 抽文本 + Vision OCR，**质量低于 markitdown** | 不做 |
| Word (.docx) | pandoc | ❌ 无可靠纯 Swift 方案 | 不做 |

> **规划影响**：格式转换应明确定位为 **macOS 独占的重活**。
> iOS 端只做「查看 + 导出 PDF（自渲染）」；需要 Word/OCR 时，把任务丢进
> **转换队列（CloudKit）**，由 Mac 端后台执行完再回传结果。
> 这恰好与第 3 条主线「固化路径以节省算力」一致——算力集中在 Mac，不在手机上重复烧。

## 五、Git 归档（第 6 条主线）在各端的落地【外部调研】

iOS 上跑 git 的现状**不乐观**：

- `SwiftGit2` **目前无法为 iOS 编译**（libgit2 依赖 libpcre，iOS SDK 未提供），且维护不活跃、仍用 fat binary 而非 XCFramework；
- `ObjectiveGit` 可用但年久；
- `MiniGit` 是较新的最小实现，**功能极简**；SwiftGit2 甚至**缺 push**。

> **规划影响**：不要在 iOS 上自己实现 git。两个可行路径：
> 1. **Mac 当归档网关**（推荐）：iOS 只管写 iCloud Drive，Mac 端应用/定时任务负责 commit+push；
> 2. **GitHub REST API**：iOS 直接调 API 提交单文件，适合「随手记一条也想立刻留痕」的场景。
>
> 当前 Python 版的 `sync.sh`/`release.sh` 逻辑可直接平移到 Mac 端。

## 六、「同一代码生态」的正确形态【外部调研】

社区 2026 年的共识不是「一套 SwiftUI 三端复用」，而是：

- **共享 Swift Package** 承载模型/存储/服务/业务逻辑；
- **各平台独立 UI target**，刻意**不**用 `#if os(...)` 硬撑一套界面；
- 共享比例是**有意识的选择**，不是越高越好。

对应到本项目：

```
LifeWorkflowKit（Swift Package · 全端共享）
├── Models        Item / ThinkingNote / RunLog / 状态机   ← 可直接从 Python 版 1:1 平移
├── Frontmatter   确定性 YAML 序列化                      ← 逻辑已验证，照搬
├── VaultStore    文件读写（macOS/iOS）
├── CloudMirror   CloudKit 投影（watchOS 用）
├── Stats         看板聚合（纯函数）
└── Services      EventKit / 转换 / 日志 / 复盘 / 归档

各端 UI：
├── LifeOS-macOS   完整功能（含转换、git、便签、多窗口）
├── LifeOS-iOS     捕捉 + 想法库 + 看板 + 快捷指令 + 小组件
└── LifeOS-watchOS 语音捕捉 + 今日一瞥 + Complication
```

> 好消息：Python 版 `lifeos/` 的**分层设计可以 1:1 平移**——
> `models.py`/`frontmatter.py`/`stats.py` 都是纯逻辑无 UI 依赖，
> 翻成 Swift 是机械工作，且已有 44 项测试定义了正确行为，可作为 Swift 测试的规格。

| 方案 | 成本 | 能做什么 | 限制 |
|------|------|----------|------|
| **不配账号** | 0 | 只能跑模拟器 | 无法装到你的 iPhone / Watch |
| **免费 Apple ID**（Personal Team） | 0 | 可装到自己的真机 | 证书 **7 天过期**，需重签；App 数量受限；部分能力（CloudKit / App Groups / 推送）**不可用** |
| **付费开发者账号** | $99/年 | 真机长期使用、TestFlight、CloudKit、小组件、Complication 全开 | 需实名与付费 |

> ⚠️ **这是必须你来决定的事**：
> 本项目的 watchOS 方案**依赖 CloudKit**，而 CloudKit **需要付费开发者账号**。
> 如果不打算付费，watchOS 端在架构上就走不通（无 iCloud Drive + 无 CloudKit = 无数据通道，
> 只剩不稳定的 WatchConnectivity）。

## 八、调研结论对原始构想的修正

| 原始设想 | 调研后的现实 | 建议调整 |
|----------|--------------|----------|
| 三端同等功能 | watchOS 能力受限严重 | 手表降级为**捕捉端 + 一瞥端** |
| 便签全端打通 | iOS 无 Notes API | 便签仅 macOS；iOS 改用**分享扩展 + 快捷指令** |
| 本地 Markdown 全端事实源 | watchOS 无文件系统 | **iCloud Drive 为事实源 + CloudKit 做手表投影**（混合模式） |
| 格式互转全端可用 | iOS 无 pandoc | 转换**集中在 Mac**，iOS 提交任务到队列 |
| Git 全端归档 | iOS 上 git 生态破碎 | **Mac 当归档网关**，或 iOS 走 GitHub API |
