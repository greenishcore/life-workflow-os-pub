# 效率与稳健性指标：先量后选，融入架构地图

日期：2026-08-20 · 状态：**已交付**

## 一、先量一遍，让数据决定选哪些指标

没有先列指标再去凑数据，而是**先把现状量了一遍**，看哪些地方真有信号。

### 静态稳健性（扫全部 Swift 源码）

| 模块 | 行数 | `try?` | 每百行 | 崩溃风险 |
|---|---:|---:|---:|---:|
| Services | 1073 | 27 | 2.5 | 1 |
| Store | 741 | 17 | 2.3 | 2 |
| Config | 133 | 3 | 2.3 | 0 |
| Shared | 653 | 10 | 1.5 | 0 |
| Frontmatter / Stats / Intents | — | 0 | 0 | 0 |

全仓 68 处 `try?`、2 处强制解包、1 处 `fatalError`、0 处 `try!`。
**Store 是数据层，17 处静默吞错意味着数据操作可能悄无声息地失败**——这是最值得看一眼的地方。

### 运行时效率（Release 构建实测）

| 项目 | 结果 | 说明 |
|---|---|---|
| vault 扫描 | 0.22 ms/条（线性） | 2000 条 = 433ms，**而每次保存后都会全量重扫** |
| frontmatter 解析 | 0.239 ms/条 | **比序列化慢 6 倍**，是热路径里的瓶颈 |
| frontmatter 序列化 | 0.040 ms/条 | |
| 思路注释的边际成本 | +0.035 ms/条 | 0→5→20→100 条完全线性，**无平方级退化**（好消息） |
| 看板聚合 | 2000 条仅 4.6 ms | 不是瓶颈 |
| 架构提取 | 63 文件 376 ms | O(文件×类型)，规模上去会变慢 |

思路注释那条值得单独说：这个项目的前提就是注释会持续累积，一条三年的想法很容易有 100+ 条注释
（单条解析 3.6ms）。好在成本是**严格线性**的，不会突然崩掉。

## 二、据此选定的三组指标

### A. 静态稳健性 —— 进 `archmap.json`（确定性）

每个模块的 `try?` / `try!` / 强制解包 / `fatalError` / `throws` / `catch` 计数，
以及**每百行密度**（比绝对值更适合横向比较）。

页面上明说了「`try?` 不一定是坏事——目录已存在就忽略是合理的」。
它是**信号不是判决**，价值在于告诉你错误在哪被静默吞掉了。

### B. 热路径基准 —— 时间序列，存 `logs/bench.jsonl`

四项，规模压到 1 秒内跑完，这样能在应用里随手点一下。
**这一点是刻意的**：这个项目已经有过教训——需要惦记着做的机制会衰减（run-log 空了三个月）。

每项带**预算**（按实测基线定，不是拍脑袋），超预算标橙。

记录里带 `configuration`（debug/release）与 `host`（机型+核数），
读取时默认只取同配置同主机的——**Debug 比 Release 慢一截（实测解析 0.32 vs 0.26 ms），
混在一条序列里趋势就没意义了**。

### C. 运行时表现 —— 从 `run-log.jsonl` 现算

不新建遥测系统：日志里已经有每次操作的耗时、成败、工具、备注，
应用自己的转换/git/提示词操作也都会自动留痕。缺的只是聚合。

按操作类型分组，给出 P50 / P95 / 成功率 / **缓存命中率**
（后者只对用了转换工具的操作统计，验证「算力经济」那条设计原则是否真的成立）。

### 过程中被自己的机制抓到的两个问题

1. **`try!` 里的 `!` 被重复计成了强制解包** —— 测试断言 `forceUnwraps == 1` 却得到 2。
   已修（跳过 `try` 后面的 `!`）并补了回归测试。
2. **新建的 `Perf/` 目录忘了在 `LayerRules` 里登记** —— **架构地图的「未覆盖目录」检测报了出来**。
   这正是那个功能存在的意义：它抓到了我自己的疏漏。

另修一处：约束理由里写了 `**加粗**`，但用纯 `Text` 渲染会把星号原样显示，改用 Markdown 渲染。

## 四、几个刻意的决定

**基准不进 CI。** GitHub 共享 runner 性能波动大，数字与本机不可比，混进时间序列只会变噪音。
基准是本地按需跑的事——页面上有「跑一次基准」按钮。就算误在 CI 跑了，
记录里的 `host` 也会让它在读取时被过滤掉。

**基准结果不进 `archmap.json`。** 那份要求确定性（CI 会 diff 它），而基准每次都不同。
同一条原则之前也用在变更频率上：**结构进版本历史，指标另行存放**。

**静态稳健性进 `archmap.json`。** 它是确定性的（同一份源码永远同一个数），
所以可以随结构一起进版本历史，将来能 `git diff` 出「这次改动多了几处静默吞错」。

## 五、这些数字支持什么决策

- **vault 扫描 0.22ms/条 + 每次保存全量重扫** → 记录数到几千条时该做增量更新或索引。现在还早，但知道拐点在哪。
- **解析比序列化慢 6 倍** → 真要优化，优化解析器，别动序列化。
- **思路注释线性无退化** → 可以放心让注释累积，这是产品前提，现在有数据背书。
- **Store 有 17 处 `try?` + 2 处强制解包** → 数据层是最不该静默失败的地方，值得逐个看一遍。
- **缓存命中率** → 验证「算力经济」不是口号。

## 六、没做

- **不做持续性能回归门禁**：共享 runner 噪音太大，会变成误报源。预算超了只标橙，不阻断。
- **不做内存/分配剖析**：需要 Instruments 级别的工具，超出「随手点一下」的定位。
- **不覆盖 Python 版**：与架构地图的既定范围一致。
