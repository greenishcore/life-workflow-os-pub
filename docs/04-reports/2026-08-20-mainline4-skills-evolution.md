# macOS 接入 App Intents + 主线 4：让 skills 演进真的转起来

## 一、macOS 接入 App Intents

把 `Intents/` 从 `Sources/iOS/` 移到 `Sources/Shared/`，两端共用。
唯一需要分平台的是 vault 从哪来，抽成 `IntentVault`：

- iOS —— 用户在文档选择器里选的目录，授权存书签
- macOS —— 配置文件里的复合多根（可能同时有 iCloud 根与本地根）

验证：macOS bundle 的 `Metadata.appintents` 里 5 个 Intent + `IdeaEntity` 全部注册（5/5）。
现在 Mac 的「快捷指令」App 与 Spotlight 也能调用这五个动作。

## 二、主线 4：信息流与 skills 演进

### 2.1 先说清楚它为什么一直是空的

路线图里 Phase 7 标的是「机制已就绪，由日常使用驱动」。但实际情况是：

**`logs/run-log.jsonl` 从来没有存在过。** 一条日志都没有。

根因不是机制缺失，是**摩擦**：记录要手动敲 `python3 scripts/log_run.py --objective ...`。
跑完一件事还要再敲一行命令，没人会持续做。日志空 → 复盘无料 → skills 无从提炼，
整条链空转了三个多月。

### 2.2 两处改动让它转起来

**改动一：应用自己的操作自动留痕。**

格式转换、git 提交推送、里程碑发布、提示词重写——这些本来就是「agent 操作」。
现在它们执行完会自动写一条 run-log，带上工具、产出、错误、耗时。
**这条链第一次有了不依赖人自觉的数据源。**

**改动二：把「提炼」从复选框变成会算东西的代码。**

原先周复盘报告末尾是三个复选框（「把高频错误写成 checklist」之类），
从没被勾过。现在 `SkillsService.propose()` 会真的算出该沉淀什么：

| 信号 | 阈值 | 产出 |
|------|------|------|
| 同一错误重复出现，现有 skill 未覆盖 | ≥ 2 次 | **沉淀避坑** —— 生成草稿，预填错误与触发条件 |
| 同一工具组合连续**成功**配合 | ≥ 3 次 | **固化流程** —— 生成草稿，附上实际成功过的场景 |
| 现有 skill 已覆盖该错误但坑仍复发 | ≥ 2 次 | **对策未生效** —— 提醒去改，不重复新建 |
| 已验证的 skill 长期未被使用 | ≥ 90 天 | **长期闲置** —— 提醒归档 |

阈值背后的判断写进了测试：错误只出现一次可能是偶然，不值得沉淀；
**失败的运行不计入流程固化**，只固化真的成功过的组合；工具组合与顺序无关。

第三条规则是我觉得最有价值的：**已经有对策但坑还在复发**，比「再建一个 skill」
更值得知道——说明那个 skill 写得不对，或者你压根没想起来用它。

### 2.3 Skill 成为一等公民

新增 `Skill` 模型，沿用仓库既有的 `skills/_template.md` 字段（`skill_id` / `name` /
`status: draft→verified→archived`），**现有 skill 文件不用改就能读进来**。
另加 `uses` / `last_used` / `source_errors` 三个字段，让「效果评分」那一环有了最小可行版本。

界面上「运行日志与复盘」页多了两张卡片：**本期可沉淀**（带「采纳」按钮，
一点就落盘成草稿）与**技能库**（状态、使用次数、闲置提醒、「记一次」）。

### 3.1 端到端跑通（这条链第一次真的产出了东西）

写了一个独立程序走完整条链，输出摘录：

```
① 起点：skills 0 条，logs 0 条
② 模拟一周操作 → 留痕 6 条
③ 聚合：成功率 66%，错误 TopN ["生成 PDF 需要 pandoc + xelatex 或 Chrome×2"]
④ 提炼：
   [沉淀避坑] 生成 PDF 需要 pandoc + xelatex 或 Chrome
      理由：这个错误重复出现 2 次且没有对应 skill…
   [固化流程] markitdown + pandoc 流程
      理由：这组工具连续成功配合了 3 次…
⑤ 采纳 → 落盘 2 个 skill 文件
⑥ skills: 2 条（不再是空的）
⑦ 下一轮同样的日志：新提议 0 条，改报「对策未生效」1 条  ← 不重复建
⑧ 记一次使用：uses=1, last_used=2026-08-20
✅ 主线 4 闭环跑通：操作 → 留痕 → 聚合 → 提炼 → 沉淀 → 复用计数
```

第 ⑦ 步是关键：证明规则不会在每次复盘时重复刷同一批提议。

### 3.2 界面

快照里「技能库」卡片正确读出了仓库现有的
`skills/convert-document.md`（已验证 · 文档格式互转 pipeline · 未用过）；
「本期可沉淀」显示的是诚实的空状态——因为 `logs/run-log.jsonl` 目前确实还是空的，
提示「用一次格式转换或版本归档，系统会自动留痕」。

顺带修了快照工具的一个盲点：`ImageRenderer` 不执行 `.task`，
所以靠它加载的数据（技能库）在截图里是空的。现在快照启动时会预热。

## 四、需要你做的一件事

**去用一次。** 这条链现在能自动收集数据了，但第一批数据得由你产生：
在 Mac 端做一次格式转换、或点一次「提交并推送」，`logs/run-log.jsonl` 就会有第一条记录。
攒够一周再看「本期可沉淀」，才知道规则在你的真实使用模式上是否合适
（阈值 2 次 / 3 次 / 90 天是我定的默认值，可能需要按你的节奏调）。

## 五、没做的事

- **Python 侧的 `weekly_review.py` 没有同步实现提炼规则**。理由：重复实现会双倍维护，
  而 Swift 版是going-forward 的实现。Python 版仍可用于聚合统计，
  但「本期可沉淀」只在应用里有。
- iOS 端没有加技能库界面——手机上定位是捕捉与查阅，复盘是 Mac 的活。
